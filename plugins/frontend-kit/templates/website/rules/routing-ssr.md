# Routing and SSR (TanStack Start)

Every page is rendered on the server first, then hydrated. Loaders and
`beforeLoad` run on the server for the first request and in the browser on
later navigations, so they must work in both places.

## Files

- `src/router.tsx` exports `getRouter()`, which returns a **new** router per
  call (one per SSR request). It creates the per-request `QueryClient` and
  i18n instance, passes them as router context, sets `defaultPreload: 'intent'`,
  `defaultPreloadStaleTime: 0`, `scrollRestoration: true`,
  `defaultErrorComponent` and `defaultNotFoundComponent`, then calls
  `setupRouterSsrQueryIntegration({ router, queryClient })`.
- `src/routes/__root.tsx` uses `createRootRouteWithContext<RouterContext>()`
  and renders the whole document: `<html lang={lang} dir={dir}>`, `<head>`
  with `<HeadContent />`, `<body>` ending in `<Scripts />`. Site-wide head
  (charset, viewport, theme-color, icons, manifest, default OG image) lives
  here; page tags live on the page route.
- `src/routeTree.gen.ts` is regenerated by the plugin on dev/build. Never edit
  it, never hand-merge it in a conflict: delete the conflict and regenerate.
- `src/start.ts` (optional) holds `createStart` with request middleware. Server functions are same-origin RPC
  endpoints: with no `start.ts` Start installs `createCsrfMiddleware()` for them automatically, but once you
  define `start.ts` you must add it yourself:

```ts
export const startInstance = createStart(() => ({
  requestMiddleware: [createCsrfMiddleware({ filter: (ctx) => ctx.handlerType === 'serverFn' })],
}))
```

## Route files are thin

```tsx
// src/routes/_site/products/$slug.tsx
export const Route = createFileRoute('/_site/products/$slug')({
  loader: ({ context, params }) => loadProductPage(context, params.slug),
  head: ({ loaderData }) => productHead(loaderData),
  component: ProductDetailContainer,
})
```

- A route file holds only: `validateSearch`, `loaderDeps`, `beforeLoad`,
  `loader`, `head`, `headers`, `component`, `pendingComponent`,
  `errorComponent`, `notFoundComponent`, `ssr`. Anything longer than a few
  lines (loader body, head builder) is a function in the feature.
- No JSX, hooks or components defined in `src/routes/`. Colocated helpers
  under `routes/` would need the `-` prefix; put them in the feature instead.
- Page hooks read the route with `getRouteApi('/_site/products/$slug')`
  (`useParams`, `useSearch`, `useLoaderData`), never by importing `Route`
  from the route file (that creates an import cycle).

## Naming conventions (file routes)

`index.tsx` = the parent path exactly · `$slug` = a param · `_site` (prefix)
= pathless layout, not in the URL · `(group)` folder = organisation only ·
`route.tsx` = a folder's own route · `[.]` escapes a dot (`sitemap[.]xml.ts`) ·
`-name` = excluded from the tree. Paths are lowercase kebab-case English
words, the same in both languages.

## Search params

- Validate every search param with a zod schema in `validateSearch`; defaults
  in the schema, never `?? ''` in components.
- Search params that change the data go in `loaderDeps` **and** the query key.
- Filters, sort and page live in the URL (shareable, back-button safe), not
  in Zustand.
- The recipe: every field `.default(x).catch(x)` (`.catch` alone makes the field
  required in every `<Link search>`), plus `stripSearchParams(defaults)` so
  defaults never leak into the URL (or into a `redirect` built from it).
- The router JSON-parses values: `?q=100553` arrives as a number and an array
  filter serialises as `brand=["Nova"]`, so an outside link `?brand=Nova` would be
  dropped. Use a `looseText` preprocess for text and ids, and a `listParam()` that
  accepts both JSON arrays and comma text. Test each list schema with a numeric
  `q` and a comma list.

## Guards and redirects

- Guards are pathless layout routes (`_account.tsx`) with `beforeLoad`
  throwing `redirect({ to: '/login', search: { redirect: location.href } })`.
  `beforeLoad` runs before every child loader, so private data never starts
  loading for a guest.
- The redirect target after login is validated as a same-site path after
  normalising (`safeRedirect`, `security.md`); never redirect to an absolute URL from the query string.
- Permanent moves (renamed slug, old URL scheme) use
  `throw redirect({ …, statusCode: 301 })`; the default is 307 (temporary).
- Never call `navigate()` in render or in a loader; on the server it is a
  no-op. Loaders throw `redirect`, user actions call `navigate` from the page hook.

## Not found and errors

- A loader that cannot find its resource throws `notFound()`. Start answers
  with HTTP **404** and renders the nearest `notFoundComponent`. Unmatched
  URLs reach the root's `notFoundComponent` (`features/fallback/not-found`).
- Thrown errors render the nearest `errorComponent` with HTTP 500. The
  shared one (`features/fallback/route-error`) shows a translated message
  and a retry that calls `router.invalidate()`; it never shows stack traces.
- Expected business states (empty list, sold out) are normal UI, not errors.
- Fallback pages are `noindex` and keep the site header and footer.

## SSR mode per route

- Default `ssr: true`: everything public stays server-rendered.
- `ssr: 'data-only'` still runs the loader on the server, so it needs the server-side session
  model; with a browser-held token use `ssr: false`. Both only for pages that are private, need
  browser-only APIs, and are `noindex` — the server then renders the route's
  `pendingComponent`, so give it the final layout size.
- Under an `ssr: false` parent (the usual account guard) the server does not run
  the child's `head()`: the guard's own `head()` is the only source of the
  `<title>` and `<meta name="robots" content="noindex">` in the HTML. Set
  `noindex` there (plus `private, no-store` and `X-Robots-Tag` in `headers()`) and
  assert it in e2e.

## Hydration: server and client must render the same thing

- No `Date.now()`, `Math.random()`, `window`, `localStorage` or
  `matchMedia` in render. Read them in an effect or wrap the part in
  `<ClientOnly fallback={…}>` with a same-size fallback.
- Dates and numbers are formatted with an explicit locale and time zone
  that the server also knows (cookie or site default), never the machine's.
- Theme (light/dark) is applied before hydration with `ScriptOnce` reading
  the stored choice; `<html>` gets `suppressHydrationWarning` for that one
  attribute only.
- Treat every hydration warning in the console as a bug.

## Language and direction

- The language comes from a cookie (fallback: the site default, Arabic),
  resolved on the server for the first render. The browser's `getRouter()`
  reads the same value back (the cookie, or the server-rendered
  `<html lang>`) through one `createIsomorphicFn` (`shared/lib/i18n/`) —
  never detected from `navigator` after load.
- `__root.tsx` renders `<html lang dir>` from that value, so the first HTML
  already has the right direction: no RTL→LTR flash, no layout shift.
- i18next is created per request (`createInstance` / `cloneInstance` with the
  resolved language) in `getRouter()`; a shared server instance switching
  language per request is a race between visitors.
- Translations for the first render are bundled (no lazy HTTP backend on the
  server), so SSR text is never the raw key.
- Switching language: set the cookie, `i18n.changeLanguage`, then
  `router.invalidate()` so loaders and `head()` re-run in the new language.
- HTML that depends on the language cookie must not be cached publicly
  under one URL (see `seo-share.md` → Languages).
